# Piper SDK 语义化版本维护策略

本文档规定 Piper SDK 的版本判定、协议迭代、公共 API 兼容和发布流程。判定依据为 [语义化版本 2.0.0 中文规范](https://semver.org/lang/zh-CN/)。

本文档中的“必须”“应该”和“可以”分别表示强制要求、推荐做法和允许选择。

## 1. SemVer 基本规则

标准版本格式为：

```text
主版本号.次版本号.修订号
X.Y.Z
```

对于已经进入稳定阶段的 `X > 0` 版本：

| 变化 | 版本变化 | 示例 |
|---|---|---|
| 不兼容的公共 API 修改 | 递增主版本号，次版本号和修订号归零 | `1.4.2 -> 2.0.0` |
| 向下兼容的功能新增或 API 弃用 | 递增次版本号，修订号归零 | `1.4.2 -> 1.5.0` |
| 仅包含向下兼容的问题修复 | 递增修订号 | `1.4.2 -> 1.4.3` |

一个发布同时包含多类变化时，采用影响级别最高的版本：

```text
不兼容修改 > 向下兼容的新功能 > 向下兼容的问题修复
```

SemVer 还要求：

- 必须定义公共 API。
- 已发布版本的内容不可修改，任何变化必须使用新版本发布。
- `0.y.z` 表示开发阶段，公共 API 不应被视为稳定。
- `1.0.0` 用于界定已经形成并准备维护的公共 API。
- 弃用公共 API 属于次版本更新；真正移除它属于主版本更新。

## 2. Piper SDK 的公共 API 范围

版本判定不能只看函数名是否变化。以下内容均属于本项目的公共兼容边界：

| 范围 | 典型内容 |
|---|---|
| 包入口 | `piper_sdk/__init__.py` 导出的类、函数、枚举和别名 |
| Interface | `C_PiperInterface`、`C_PiperInterface_V2`、`C_PiperInterface_V3` 的公开方法 |
| Protocol 和 message | 可由用户直接导入的 parser、消息类、CAN ID、消息类型和映射 |
| 调用签名 | 参数名称、顺序、必填性、默认值、类型和关键字调用方式 |
| 可观察行为 | 返回值、异常类型、状态共享、单例行为、线程行为和默认操作 |
| 枚举 | 成员名称及用户可能依赖或序列化的 `.value` |
| CLI | 命令名称、子命令、参数、选项、默认值、退出码和输出契约 |
| 运行环境 | 最低 Python 版本、支持的平台和必要系统依赖 |
| 硬件兼容 | 已声明支持的机械臂固件、CAN 协议和设备选择方式 |

以下内容通常不属于公共 API，但修改后仍需验证没有外部影响：

- 双下划线私有方法和未导出的内部辅助函数。
- 仅用于实现的锁、缓存和临时消息对象。
- 测试代码、CI 配置和内部开发文档。
- 不改变构建结果的格式化和注释。

Python 可以从实现模块导入未正式导出的名称，但本项目只承诺文档明确列出、包入口导出或长期公开使用的接口。低层导入路径发生变化时仍应评估实际用户影响。

## 3. 协议更新如何判定版本

协议变化本身不直接决定版本级别。应判断它是否改变现有用户的公共 API、已有固件支持或运行结果。

| 协议更新场景 | 用户影响 | `0.y.z` 策略 | `1.0.0+` 策略 |
|---|---|---|---|
| 只修正文档中的 CAN ID、单位或位说明，代码行为不变 | 无运行时影响 | 修订号 | 修订号 |
| 修复 parser 对已有协议的错误解析 | 正确调用兼容，错误结果被修正 | 修订号 | 修订号 |
| 修复 encoder 生成错误帧的问题 | 正确调用兼容，错误帧被修正 | 修订号 | 修订号 |
| 在现有协议类中新增可选 CAN 帧或查询能力 | 旧功能不变，新能力可选 | 次版本号 | 次版本号 |
| 新增独立的 V3 parser、message 和 interface | V2 保持不变，用户主动选择 V3 | 次版本号 | 次版本号 |
| 自动识别新协议，同时继续正确支持旧固件 | 旧用法不变，新硬件可用 | 次版本号 | 次版本号 |
| 用新协议替换旧协议，导致旧固件不能工作 | 原有硬件兼容被破坏 | 次版本号并标记 Breaking Change | 主版本号 |
| 修改已有方法的报文编码，使同一调用产生不同协议语义 | 现有调用结果变化 | 次版本号并标记 Breaking Change | 主版本号 |
| 固件改变 raw 单位，SDK 只更新注释 | 运行时不变 | 修订号 | 修订号 |
| 固件改变 raw 单位，SDK 修改自动换算但保持物理语义 | 通常属于错误修复，需验证边界 | 修订号；高风险时可用次版本号 | 修订号；高风险时可用次版本号 |
| 固件改变 raw 单位，已有 raw 参数的含义直接改变 | 调用结果不兼容 | 次版本号并标记 Breaking Change | 主版本号 |

### 3.1 推荐的多协议设计

新协议应优先采用显式版本入口：

```python
from piper_sdk import C_PiperInterface_V2
from piper_sdk import C_PiperInterface_V3
```

推荐原则：

- 保留 V2 的类、默认导出和既有行为。
- 新增 V3 类和版本化的 message/parser 别名。
- 新协议由用户显式选择，或者由可靠且向后兼容的检测机制选择。
- 不允许 V3 的同名导入静默覆盖原有 V2 顶层导出。
- V3 可以继承 V2 的内部实现，但不能因此意外改变 V2 的公共行为。

满足以上条件时，即使 V3 的线协议变化很大，对 SDK 版本而言仍是向下兼容的功能新增。

## 4. 代码特性更新如何判定版本

### 4.1 公共 API

| 代码变化 | `0.y.z` 策略 | `1.0.0+` 策略 |
|---|---|---|
| 新增类、方法、可选参数或版本化别名 | 次版本号 | 次版本号 |
| 新增 CLI 或子命令 | 次版本号 | 次版本号 |
| 新增可选功能且默认关闭 | 次版本号 | 次版本号 |
| 标记 API 弃用但仍可使用 | 次版本号 | 次版本号 |
| 删除、重命名公开类或方法 | 次版本号并标记 Breaking Change | 主版本号 |
| 删除参数默认值，使参数变为必填 | 次版本号并标记 Breaking Change | 主版本号 |
| 改变参数顺序、名称或位置/关键字调用方式 | 次版本号并标记 Breaking Change | 主版本号 |
| 修改默认值并改变正常调用结果 | 次版本号并标记 Breaking Change | 主版本号 |
| 缩小合法输入范围或新增异常 | 视影响使用修订号或次版本号，并明确说明 | 通常为主版本号；若只是拒绝明确非法输入可评估为修订号 |
| 改变返回值类型、结构或单位 | 次版本号并标记 Breaking Change | 主版本号 |
| 改变公开枚举成员名称或数值 | 次版本号并标记 Breaking Change | 主版本号 |
| 新增 `auto()` 枚举成员导致旧成员数值位移 | 次版本号并标记 Breaking Change | 主版本号 |
| 改变对象单例、共享状态或身份语义 | 次版本号并标记 Breaking Change | 主版本号 |
| 修改顶层导出默认指向的协议版本 | 次版本号并标记 Breaking Change | 主版本号 |

### 4.2 问题修复和内部实现

| 代码变化 | 推荐级别 |
|---|---|
| 修复异常崩溃、错误计算或错误报文 | 修订号 |
| 修复线程竞争、资源泄漏或重复初始化 | 修订号 |
| 修复异常数据过滤和状态同步 | 修订号 |
| 仅重构私有实现，公共行为不变 | 修订号或不单独发布 |
| 性能优化，结果和资源契约不变 | 修订号 |
| 大规模内部改进并带来明显新能力 | 次版本号 |
| 安全修复且兼容现有 API | 修订号 |
| 安全修复必须破坏现有 API | `0.y.z` 使用次版本号并说明；稳定版使用主版本号 |

修复错误通常会让输出与旧版本不同。只要旧输出明确违反协议或文档，且正确调用方式不变，可以作为修订更新。若大量用户可能依赖旧行为，应提升发布级别、提供迁移说明，或者先加入兼容和弃用周期。

### 4.3 文档、demo、测试和构建

| 变化 | 推荐级别 |
|---|---|
| 只修正文档、注释、拼写或 demo 说明 | 修订号或不单独发布 |
| 新功能对应的文档和 demo | 跟随该功能的次版本发布 |
| 新增测试但不改变发行代码 | 不单独发布或修订号 |
| 修复 wheel/sdist 缺文件、入口点或安装失败 | 修订号 |
| 新增可选 CLI 入口或打包能力 | 次版本号 |
| 仅调整 CI、lint 或格式化 | 不单独发布或修订号 |

### 4.4 依赖和运行环境

| 变化 | `0.y.z` 策略 | `1.0.0+` 策略 |
|---|---|---|
| 为修复问题兼容性更新依赖 | 修订号 | 修订号 |
| 为新功能增加必要依赖 | 次版本号 | 次版本号 |
| 增加可选依赖，旧安装仍工作 | 次版本号 | 次版本号 |
| 提高最低 Python 版本 | 次版本号并标记 Breaking Change | 主版本号 |
| 移除已支持的平台或系统后端 | 次版本号并标记 Breaking Change | 主版本号 |
| 扩展 Python、系统或硬件支持 | 次版本号 | 次版本号 |

## 5. `0.y.z` 开发阶段策略

SemVer 只明确规定 `0.y.z` 处于开发阶段，并没有像 `X > 0` 一样强制规定每一种变化如何映射到 Y 和 Z。为保持 Piper SDK 的版本可预测性，本项目采用以下额外约定。

### 5.1 项目约定

| 更新类型 | 版本策略 | 示例 |
|---|---|---|
| 只有向下兼容的问题修复 | 递增修订号 | `0.6.3 -> 0.6.4` |
| 新增协议、API、CLI 或用户功能 | 递增次版本号，修订号归零 | `0.6.3 -> 0.7.0` |
| 包含不兼容修改 | 递增次版本号，修订号归零，并在 CHANGELOG 标记 Breaking Changes | `0.6.3 -> 0.7.0` |
| 从开发阶段进入稳定 API | 发布 `1.0.0` | `0.7.0 -> 1.0.0` |

在 `0.y.z` 阶段，次版本号同时承担“新功能”和“开发期不兼容调整”的表达责任。不能因为 SemVer 允许开发期变化就隐藏破坏性修改；仍必须提供迁移说明。

### 5.2 常见场景

假设当前正式版本为 `0.6.3`：

| 发布内容 | 下一版本 |
|---|---|
| 只修复 V2 内部 bug | `0.6.4` |
| V2 不变，只新增独立 V3 支持 | `0.7.0` |
| 新增 V3，同时兼容性修复 V2 | `0.7.0` |
| 新增 V3，同时修改 V2 方法签名 | `0.7.0`，必须标记 Breaking Changes |
| 只修改 V2 方法签名或默认行为 | `0.7.0`，必须标记 Breaking Changes |
| 只修正文档和注释 | `0.6.4` 或不单独发布 |
| 决定从此承诺公共 API 稳定 | `1.0.0` |

### 5.3 何时发布 `1.0.0`

发布 `1.0.0` 不表示协议或代码以后不再更新，而表示从该版本开始承诺维护公共 API。

建议满足以下条件：

- 正式使用场景中的核心 API 已形成。
- V2/V3 的选择方式、导出和兼容边界明确。
- 公开方法的参数、单位、默认值和异常已文档化。
- 主要协议路径有自动测试和实际硬件验证。
- 后续不兼容修改愿意通过新的主版本发布。
- 已知不稳定的实验接口已标记为 experimental 或未纳入稳定 API。

## 6. `1.0.0` 及以后策略

从 `1.0.0` 开始严格执行 SemVer 的主版本、次版本和修订版本规则。

### 6.1 常见场景

假设当前正式版本为 `1.0.0`：

| 发布内容 | 下一版本 |
|---|---|
| 只修复 V2 内部 bug，API 兼容 | `1.0.1` |
| V2 不变，只新增独立 V3 支持 | `1.1.0` |
| 新增 V3，同时兼容性修复 V2 | `1.1.0` |
| 新增可选 CLI 或新子命令 | `1.1.0` |
| 弃用旧 API，但暂不删除 | `1.1.0` |
| 修改 V2 方法签名、默认行为或顶层导出 | `2.0.0` |
| 删除旧协议、Python 版本或平台支持 | `2.0.0` |
| 修复文档或构建缺文件 | `1.0.1` |

假设当前正式版本为 `1.4.2`：

```text
兼容修复       -> 1.4.3
兼容新功能     -> 1.5.0
任何不兼容修改 -> 2.0.0
```

主版本升级可以同时包含新功能和问题修复。次版本升级也可以同时包含修订级别的问题修复。

## 7. 混合更新的判定方法

实际发布通常包含协议、新功能和修复，应按以下顺序判定：

1. 以“上一个已正式发布的 tag”作为比较基线，而不是以某个开发 commit 或分支名作为基线。
2. 列出所有公共 API、协议兼容、运行环境和行为变化。
3. 判断是否存在任何不兼容变化。
4. 若无不兼容变化，判断是否新增用户可用功能。
5. 若既无不兼容变化也无新功能，判断是否只有兼容修复。
6. 按最高影响级别选择整个发布的版本号。

示例：

| 组合 | `0.y.z` | `1.0.0+` |
|---|---|---|
| V3 新功能 + V2 bug 修复 + 文档 | 次版本号 | 次版本号 |
| V3 新功能 + V2 不兼容签名修改 | 次版本号并标记 Breaking Change | 主版本号 |
| V2 bug 修复 + 测试 + 文档 | 修订号 | 修订号 |
| 新 CLI + 构建修复 | 次版本号 | 次版本号 |
| 平台移除 + 任意新功能 | 次版本号并标记 Breaking Change | 主版本号 |

## 8. Piper SDK 具体案例

### 8.1 新增 V3，同时保留 V2

如果以下旧代码继续正常工作：

```python
from piper_sdk import C_PiperInterface_V2

piper = C_PiperInterface_V2("can0")
```

而新协议通过以下方式主动选择：

```python
from piper_sdk import C_PiperInterface_V3

piper = C_PiperInterface_V3("can0")
```

则它属于兼容的新功能：

```text
0.6.3 -> 0.7.0
1.0.0 -> 1.1.0
```

### 8.2 开发 V3 时同步修复 V2

若 V2 修改仅修复线程竞争、异常过滤、状态同步或错误解析，且正确的旧调用仍兼容，则这些是修订级别修复。因为同一发布还包含 V3 新功能，最终发布仍采用次版本号：

```text
0.6.3 -> 0.7.0
1.0.0 -> 1.1.0
```

不需要为了符合研发顺序，强制先发布一个 V2 修复版本。只有 V2 修复紧急而 V3 尚未完成时，才建议从旧 tag 建维护分支，先发布例如 `0.6.4` 或 `1.0.1`，再把修复合并到 V3 分支。

### 8.3 `MotorMaxSpdSet` 参数改为必填

从有默认值改为显式必填会让旧调用抛出 `TypeError`，属于不兼容的公共 API 修改：

```python
# 旧调用
piper.MotorMaxSpdSet()

# 新调用
piper.MotorMaxSpdSet(6, 300)
```

版本策略：

```text
0.6.3 -> 0.7.0，并在 CHANGELOG 标记 Breaking Change
1.x.y -> 2.0.0
```

底层组合报文接口保留 `0x7FFF` 无效值默认参数，不代表高层速度设置接口也应默认执行空操作。

### 8.4 顶层协议类型被覆盖

如果 `from piper_sdk import ArmMsgFeedbackStatusEnum` 从 V2 静默变成 V3，即使名称不变，也属于不兼容修改。应优先修复为原默认导出不变，并提供明确的 `_V2`、`_V3` 别名。

### 8.5 枚举 `auto()` 插入成员

在已有成员前插入新的 `auto()` 成员可能改变旧成员 `.value`。若数值可能被记录、序列化或外部比较，应显式固定枚举值，或者将该变化视为不兼容修改。

### 8.6 单例改为实例独立

将参数管理器从全局单例改成实例独立可以修复多设备状态污染，但对象身份和共享状态行为发生变化。若该行为属于公开契约，则按不兼容修改处理；若从未公开且只修复内部错误，可以作为修订处理，但必须有回归测试并在 CHANGELOG 说明。

## 9. 先行版本和 Beta 分支

SemVer 先行版本示例：

```text
0.7.0-alpha.1
0.7.0-beta.1
0.7.0-rc.1
0.7.0
```

Python 包发布还需要符合 PEP 440，推荐在 `setup.py` 中使用：

```text
0.7.0a1
0.7.0b1
0.7.0rc1
0.7.0
```

先行版本表示功能尚未稳定，可能不满足最终兼容要求。正式发布 `0.7.0` 后，不可再修改同一个版本的发行内容，任何修复必须发布新版本。

分支名和 commit message 可以包含开发时的暂定版本，例如 `1_0_0_b1`。如果最终决定发布 `0.7.0`，不必仅为版本文本重写全部历史 commit；必须保证最终源码、包元数据、CHANGELOG、tag 和发布产物统一为 `0.7.0`。

## 10. Commit 与发布组织

版本号根据最终发布差异确定，不根据 commit 数量或研发先后确定。推荐将 commit 按职责拆分：

```text
refactor(v2): expose protected hooks for protocol extension
fix(v2): filter abnormal feedback before clamping
fix(v2): isolate transmit state per thread
feat(v3): add V3 messages and parser
feat(v3): add C_PiperInterface_V3
feat(cli): add piper-can commands
docs(v3): add protocol and demo documentation
```

这种组织允许 V2 紧急修复单独 cherry-pick 到维护分支，但不要求每一组 commit 都单独发布版本。

## 11. 发布检查清单

发布前必须完成以下检查：

- 以最近正式 tag 对比全部代码和公共行为。
- 确认 V2/V3 顶层导出没有意外覆盖。
- 检查公开方法的参数、默认值、返回值和异常变化。
- 检查枚举成员和值是否发生位移。
- 检查支持的固件、Python、平台和依赖是否变化。
- 将不兼容变化单独列入 CHANGELOG 的 Breaking Changes。
- 同步 `setup.py`、`piper_sdk/version.py`、CHANGELOG 和相关 demo README。
- 保留历史版本枚举，不要直接删除已发布版本成员。
- 清理旧的 `build/`、`dist/` 和 `*.egg-info/` 后重新构建。
- 验证 wheel 和 sdist 中的版本号、CLI、Shell 脚本、文档和包数据。
- 运行自动测试、导入测试、CLI 测试和必要的真实硬件测试。
- 创建与发布版本一致的 Git tag 和 GitHub Release。
- 已发布版本禁止覆盖上传；发现问题后递增版本重新发布。

## 12. 快速决策表

| 问题 | 是 | 否 |
|---|---|---|
| 是否破坏旧 API、旧固件、默认行为或支持环境？ | `0.y.z` 升次版本并标记 Breaking；稳定版升主版本 | 继续判断 |
| 是否新增协议、API、CLI、硬件支持或用户能力？ | 升次版本 | 继续判断 |
| 是否只修复错误且保持兼容？ | 升修订号 | 继续判断 |
| 是否只有测试、格式或内部文档变化？ | 可以不发布，或随下一版本发布 | 重新确认变化范围 |

## 13. 本项目当前策略结论

在公共 API 仍处于开发阶段时，Piper SDK 采用：

```text
兼容修复                     -> 0.y.(z+1)
新协议、新功能或开发期破坏性调整 -> 0.(y+1).0
公共 API 正式形成             -> 1.0.0
```

进入 `1.0.0` 后采用严格 SemVer：

```text
兼容修复     -> x.y.(z+1)
兼容新功能   -> x.(y+1).0
不兼容修改   -> (x+1).0.0
```

协议版本号、固件版本号和 SDK 包版本号是三个不同概念。V3 协议不要求 SDK 必须发布为 `3.0.0`；SDK 版本只由对 SDK 用户的兼容性和功能影响决定。
